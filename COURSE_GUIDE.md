# How to work through the lessons

## Start with one lesson

Open [Lesson 01](modules/01-python-engineering.md). Follow the sequence through Lesson 12, taking time to understand each worked example before trying the next idea.

The lessons share a fictional business called Maple Books. Its approved facts stay consistent. Wrong answers, old drafts, and new pretend tool capabilities are labeled in the lesson so you can distinguish them from the source facts.

Each lesson follows the same pattern:

1. Read the introduction and learning objectives.
2. Follow the explanation and worked example.
3. Try the small activity.
4. Complete the assignment in your own words.
5. Attempt the knowledge check before opening the answers.

You can spread a lesson across several study sessions. There is no fixed deadline.

## What you need

A notebook or text document is enough for the written activities. A spreadsheet can help with tables but is optional.

You can try prompts in an AI chat tool you already use. Save the actual replies if you do. The supplied replies and result tables are authored teaching examples, not recorded model experiments.

The action exercises use pretend orders and stored drafts. They do not change a real shop system.

## Keep a small learning folder

| Lessons | What to keep |
|---|---|
| 01–03 | Your assistant idea, response comparison, and prompt experiment |
| 04–06 | Questions, expected behavior, review rules, and reviewed replies |
| 07–09 | Source passages, paired comparison, and pretend action workflow |
| 10–12 | Difficult scenarios, investigation record, and final project |

Keep raw replies unchanged and explain the reasons for your judgments. Label examples as supplied, simulated, or actually observed.

## How to judge your progress

You are ready to move on when you can explain the lesson's idea and give a reason for the outcome of an example.

For instance, say: “This answer invents an express-delivery price because the source does not describe that service.” The reasoning matters more than repeating a term.

If an exercise is confusing, reread its walkthrough and try explaining it aloud. Use the glossary only for the word you need.

## Begin with a few examples

Start with a handful of questions you can inspect fully. The small suggested collection sizes are learning targets, not proof of reliability.

Include missing-information and incomplete-request cases as well as straightforward questions. An answer that correctly explains a limitation can be successful.

Keep some questions for improving the prompt and a few fresh questions for a later check. If the fresh questions influence another revision, record that they have entered the development process.

## A workable solo-review path

If another person can help, ask them to judge examples independently using the same facts and rules before discussing differences.

If you study alone, review a few examples again after a break with their order changed. Keep the original judgments and note what changed. This is solo practice, not independent agreement between reviewers.

A model reviewer can help but can also be wrong. Keep disagreements and uncertain cases visible rather than forcing a favorable result.

## Where Python fits

Python remains the language for implementation and automation.

Lesson 05 shows a short optional program that counts review outcomes. It does not judge truth or call a model. You can skip it during the first reading.

When ready to program, begin with a small familiar task: store examples, print a summary, read a file, then add a model adapter. The [technical notes](advanced/README.md) and [setup guide](SETUP.md) provide the deeper material.

The written path builds understanding. To demonstrate a working AI system, you will also need programming practice, an actual implementation, and recorded results.

## Finish with an honest project

Lesson 12 lets you choose a written prototype first or a working implementation. Say clearly which one you completed.

Keep your problem, sources, prompts, questions, reviewed outcomes, one improvement, and one informative failure. State what remains untested. You can then expand into a larger [project brief](projects/README.md) when ready.
